# Исследовательский прогон (paper trading)

## Зачем это нужно

В бою за 9 дней прошло **4–5 сделок**, винрейт 0%. На такой выборке невозможно
отличить полосу неудач от системного минуса — четыре сделки не доказывают ничего.

Замеры по `logs/app.log` (61 026 снимков за 2 недели) показали, что подходящих
моментов было гораздо больше, но их резал сломанный фильтр глубины: **50.2%**
спредов ≥1.3% отклонялись *только* по нему. После фикса поток должен вырасти
примерно **в 7–16 раз**.

Прогонять это сразу в бою нельзя: если минус структурный, мы начнём терять в 16 раз
быстрее. Поэтому сначала — на бумаге, на реальных рыночных данных.

## Результаты прогона №1 (99 сделок)

```
Сделок: 99 | винрейт: 5.1% | P&L: -2.4122 USDT | средний: -0.0244
```

Три вывода:

**1. Bitget отравлял выборку.** Участвовал в 55 сделках и дал 95% всего убытка:

| | сделок | P&L | средний |
|---|---|---|---|
| с bitget | 55 | −2.2898 | −0.0416 |
| без bitget | 44 | −0.1222 | **−0.0028** (в 15 раз лучше) |

Причина, вероятно, в качестве потока: 388 обрывов WS против 3 у binance. Между
обрывами котировки замирают → видим расхождение с ценой, которой уже нет →
входим в фантомный спред. **Bitget отключён во втором прогоне.**

**2. Разложение P&L не сходилось.** По компонентам выходил плюс 0.474%, фактически
был минус 0.910% — терялось 1.384% на сделку. Не хватало строки «отдано на выходе»:
56 из 99 сделок закрылись по `max_adverse`, то есть расхождение продолжало расти,
а не возвращалось. Отчёт исправлен, теперь есть контроль сходимости.

**3. Сделки с `target` тоже в минусе** (−0.0276 при среднем −0.0244). Это значит,
что даже когда спред сходится ровно по плану, цена входа настолько плоха, что это
не спасает. Доработками логики выхода такое не лечится.

## Что запустить

На сервере, рядом с боевым ботом (они не конфликтуют — разные файлы БД и логов):

```bash
python -m arb.main --config config.research.yaml
```

Оставить на **сутки-двое**. Ожидаемо наберётся несколько сотен бумажных сделок.

Полезно запустить под `screen`/`tmux` или через systemd, чтобы не оборвалось
вместе с ssh-сессией:

```bash
screen -S research -dm python -m arb.main --config config.research.yaml
screen -r research     # подключиться и посмотреть
```

## Чем отличается от боевого конфига

Пороги входа **специально те же**, что в бою: мы измеряем текущую стратегию, а не
подгоняем её под красивый результат. Отличается только то, что мешало бы замеру:

| Параметр | Бой | Исследование | Почему |
|---|---|---|---|
| `dry_run` | false | **true** | реальные деньги не участвуют |
| `one_shot_per_pair` | true | **false** | возможности сконцентрированы в 5–10 парах; в бою каждая «сгорала» после одной сделки |
| `max_concurrent_positions` | 10 | **0** (без лимита) | лимит резал бы выборку |
| `cooldown` | 1 | **0** | повторные расхождения по паре нужны для статистики |
| `max_hold_time` | 604800 | **3600** | не держать бумажную позицию неделю |
| `profit_buffer_close` | true | **false** | неттинг искажает чистый P&L |
| `telegram.enabled` | true | **false** | иначе сотни уведомлений |
| БД / логи | `trades.db` | `research_trades.db` | боевая статистика не смешивается |

Важно, что осталось включённым: `simulate_slippage: true` — исполнение считается по
**реальному стакану**, а не по идеальной цене сигнала. Без этого бумажный P&L был бы
фантазией и весь замер обесценился.

## Как разобрать результат

Через сутки:

```bash
python -m arb.main --config config.research.yaml --analyze
```

Отчёт покажет разложение P&L по шагам: сырой спред → слиппедж входа → слиппедж
выхода → комиссии → funding → фактический результат. Плюс разбивку по причинам
закрытия, парам и маршрутам бирж.

## Что мы ищем в цифрах

Главный вопрос — **на что уходит сырой спред**. Три исхода:

1. **Съедает слиппедж входа** (ожидаемо по прошлым данным: 1.71% против 1.558%
   сырого спреда). Значит проблема в цене исполнения, а не в частоте сигналов, и
   дальше нужно переходить на лимит-ордера — крутить пороги бессмысленно.

2. **Плюс есть, но только на части пар/маршрутов.** Тогда сужаем вселенную:
   `allow_list` под конкретные пары, отключение убыточных бирж.

3. **Плюс есть в целом.** Тогда осторожно повышаем объём в бою, начиная с
   `max_notional_per_leg` и `max_concurrent_positions`, не меняя пороги входа.

Отдельно стоит посмотреть, не концентрируется ли минус в тонких неликвидных
монетах (EUL, AKE, HOME, O, BARD — они давали самые широкие спреды). Сломанный
фильтр глубины раньше случайно нас от них защищал; теперь этого предохранителя нет.

## Чего НЕ делать по ходу прогона

- Не подкручивать пороги «чтобы было больше сделок» — испортится выборка.
- Не переносить `config.research.yaml` в бой: `dry_run: true` и снятые лимиты
  риска там опасны.
- Не смешивать: `--analyze` без `--config config.research.yaml` покажет боевую БД.
